# Security review, batch 8b (UM-063): the broker adapters, the MCP write tools and the code flow of 2026-11-04

Not to be confused with `backend/docs/security-review-batch8.md`, the review of contract 0.0.13 (CT-099), whose findings are `B8-F1` to `B8-F4`. This one is written by the author of most of the code under review, so it
is a self-review: it reads each piece as an attacker would, and it fixes what it finds with a test that failed before the fix. A review by another session is still open. Findings here are `B8b-n`.

Scope (read, then fixed): the broker adapters `oauth-scoped`, `postgres-readonly`, `cloud-folder-share`, `messaging-subaccount`, `hosting-subaccount`, `saas-seat-scim` and `newsletter-reader`, with the
shared `provider/manager.ts` and `provider/http.ts`; the write tools of `@x207/mcp` (SD-082) and its HTTP server; the one-time code flow (UM-094, UM-100, UM-101). Looked for: a secret that reaches a log, an
error or an API answer; a scope that can be passed; SSRF to the URL of a provider; replay of a grant; a race of revoke.

Levels as in batches 2, 4 and 7.

## Read and found sound (no change)
- **Scope cannot be passed.** `cloud-folder-share`: the folder is matched segment by segment against `allowedFolders` (`projects/alphabet` is not inside `projects/alpha`), `..`, `.`, empty segments, a leading slash and non-ASCII are refused, and every segment is URL-encoded. `hosting-subaccount` and `messaging-subaccount`: the quotas are integers or fixed-point text under the caps of the operator. `oauth-scoped`: every scope must be on the list, and a provider that answers with a wider scope has its token revoked at once. `saas-seat-scim`: the group is an exact id on the list; a user that already exists (`409`) is never taken over, so a revoke can not delete a real person. `newsletter-reader`: only the exact paid tiers; a reader that already pays elsewhere is not touched; a member that existed before is downgraded, never deleted. `postgres-readonly`: schema and table names are checked against `[a-z_][a-z0-9_]*`, then quoted; the role name is derived from the grant id and never from what a person wrote; the system schemas are refused whatever the list says; the statement that holds the password is never in an error.
- **Ids that come back from a provider** (`id` of a sub-account, an account, a share, a user) are checked against `[A-Za-z0-9_-]{1,128}` before they go into a path, and a handle is parsed with the same rule, so an answer of a provider cannot make the broker call another endpoint.
- **SSRF to the URL of a provider.** The base URLs and the endpoints of the adapters are set by the operator, must be `https`, and are never taken from a grant, a scope or an answer. A redirect that leaves the host does not carry the `Authorization` header (the platform removes it).
- **Replay of a grant.** A day is paid with a voucher whose `seq` the facilitator moves up; the rent of a day goes through the per-grant queue; `sharedKey` stops a second live grant for the same thing (folder and person, seat, reader).
- **Hosted mode.** All seven adapters declare `real = true`, so a hosted broker refuses them.
- **The code flow (UM-094, UM-100, UM-101).** The check route keeps the protections of batch 7 (a signed notice that is used once, 30 checks an hour, the HMAC of the code, a reservation before the issuer is asked, a timeout, a log line with the name of the issuer only). The three sandbox tests search every table of the read model and the console for the codes, the salts and the file keys, and find none. The new issuers of the tests (an expired promo code, a gift card with a balance) go through the same route and answer `code_unknown` or `code_used` before any key is released; no new path was added to the backend.
- **MCP write tools.** No result, error or log holds a configured key (every text is scrubbed, tested with an error that carries both keys). The budget, the price cap, the counterparty check and the key check run before anything is signed; a bundle is signed only when the hash of the terms equals the hash the backend sent; a listing from the book is used only when it hashes to the hash that was asked for.

## Limits that are written down, not fixed
- **`oauth-scoped` keeps the token in its handle** (needed to revoke after a restart), in the sqlite of the broker, until BK-010 (sealing to a TEE). Documented in `docs/security.md`.
- **`oauth-scoped` renewal** makes a new token and revokes the old one; when that revoke fails the failure is ignored, so the old token lives until its own end (at most the paid day it was made for).
- **`postgres-readonly`**: `default_transaction_read_only = on` is a default that the role may change; what stops a write is that the role has only `SELECT`. On PostgreSQL 14 or older `PUBLIC` may create objects in the schema `public`: the role could create a table there, which `DROP OWNED BY` removes at the revoke. A session that is open when the paid day ends stays open until the broker ends it.
- **The queues are per process.** The per-grant queue of the manager and the per-group writer of the SCIM adapter protect one broker process; two broker processes on one database or one SCIM tenant are not covered.
- **The session budget of the MCP server lives in the memory of the process.** Restarting the server starts a new budget; the operator who restarts it in a loop gives the agent a new budget each time. The balance of the agent account is the limit that does not reset (see the README of `@x207/mcp`).
- **A provider answer in an error is cut at 160 characters** after the request credential is taken out; it may still say things about the provider that the lessee sees in `lastError`.

## Not covered
Another session has not read this. Real providers were not used: every adapter ran against a mock written by the same author, so a provider that behaves in a way that the mock does not (for instance a SCIM service that rejects `PUT` of a group) is not tested.
