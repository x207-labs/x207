# What has and has not run

_Moved from the first README and kept up to date with the README and the chain (UM-120). Paths are relative to this folder. Start at the [README](../README.md)._

**History of the rehearsals (the status paragraph of the first README).** Hackathon prototype for NEAR HACKATHON (1–14 Nov 2026). Almost everything runs in a local `near-sandbox`. Two testnet rehearsals ran: F1 to F4 on 2026-11-02 against an old rehearsal contract, and the barter flow (F5 ring, F9 quick barter, clearing, residual, finalize, claims) on 2026-11-03 against contract 0.0.7 (`x207-circle-v7.testnet`, mock USDT, no NEAR Intents). The network demo (`npm run demo:testnet` with its options) also ran one full epoch on testnet on 2026-11-03 with the barter ring, a gas key, clearing, a debtor that did not pay and a DAO vote on `set_params`, on its own circle with a mock USDT. Separate testnet runs covered the access assets of F8 (v9), the `exact` payment of a buyer outside the circle, and a gas key with four parallel lanes. Since then the contract was released as v0.0.13 (interface 0.0.13) and runs as the circle `x207-v013.testnet`: the load test (epoch 2, 210 obligations) and the realistic epoch 8 (24 vouchers, five of six debtors paid, one default) ran on it on 2026-11-04. No mainnet transaction has been sent, and each section says what has and has not run.

### Epoch timeline of the circle

These are the values that `get_params` returns for `x207-v013.testnet` (read on 2026-11-04 and recorded in [docs/testnet-params.json](testnet-params.json); the command is in [docs/testnet.md](testnet.md)). `npm run check:numbers` compares the figures below with that record and, when online, with the chain. The circle runs shorter times than the contract's built-in defaults in `contracts/x207-circle/src/params.rs` (ADR-25: 3600, 1800 and 600 seconds), so a cycle fits in a demo. `set_params` can change them only inside the ranges coded in the contract (ADR-20).

| Parameter | Value | Where it applies |
| --- | --- | --- |
| `epoch_length` | 600 s (10 minutes) | From the start of the epoch to the cutoff |
| `proposal_window` | 60 s (1 minute) | After the cutoff, any solver can submit a clearing proposal |
| `payment_window` | 900 s (15 minutes) | After `commit_epoch`, net debtors pay the residual |
| `prune_delay_epochs` | 3 | `prune_epoch` refuses with `ERR_PRUNE_TOO_EARLY` until three epochs have passed (it was 2 until epoch 20; a DAO vote changed it, see [governance-live.md](governance-live.md)) |

The DAO proposal period (1 hour on the DAO `x207v8.sputnikv2.testnet`) is a Sputnik setting, not a contract parameter. The other parameters (`base_limit_ratio` 8000, `limit_growth` 1000, `limit_cap` 1000000000, `limit_decay` 0, fees `clearing_fee_bps` 0 and `solver_fee_bps` 0 (10 and 5 until epoch 47; DAO proposal 5, [governance-live.md](governance-live.md)), `admission` open, `bond_threshold` 100000000, `bond_bps` 2000, `max_search_share_bps` 500) are in the same record.

T0 is the moment the epoch opens.

| Time | Stage | What happens |
| --- | --- | --- |
| T+0:00 | Epoch open | Agents pay with vouchers, and the facilitator registers each pair before the cutoff |
| T+0:10 | Cutoff | A keeper calls `close_epoch`. The obligations are frozen and the next epoch opens |
| T+0:10 to T+0:11 | `proposal_window` | A solver simulates and submits the clearing |
| T+0:11 | Commit | A keeper calls `commit_epoch`. The 207 report is available |
| T+0:11 to T+0:26 | `payment_window` | Net debtors pay. A debtor that does not pay will default |
| T+0:26 | Finalize | A keeper calls `finalize_epoch`. Defaults are covered by stake, and creditor positions become claimable |

One full cycle takes 26 minutes from the opening of the epoch to finalization, plus the time to claim.
