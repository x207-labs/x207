# Details moved out of the README

The [README](../README.md) keeps the short version. This page holds the long paragraphs that used to sit at its top: what is new, the status of every circle, and the history of contract 0.0.18.

## Which version is which

- **Interface 0.0.13, release v0.0.13:** the first contract release, the circle `x207-v013.testnet`. It is the circle behind epoch 8 and the Read API at `x207.boxd.sh`.
- **Contract 0.0.18, circle `v018`:** the latest release, the circle `x207-v018.testnet` (tag `v0.0.18`). The barter ring of epoch 184 and the marketplace ran on it. In the dashboard URL, `circle=v018` selects this circle.
- The versions in between (v014 to v017) are circles of their own on testnet, listed below.

## What is new

(1) A multi-party binding of the x402 `batch-settlement` scheme on NEAR, as far as we found (the proposal is [x402-foundation/x402#4131](https://github.com/x402-foundation/x402/issues/4131); nobody has accepted it yet). (2) Cumulative vouchers that are netted once per epoch across many buyers and sellers. (3) One stake covers sellers that are not known in advance, where a channel per seller needs a deposit for each ([the comparison, spike S1](problem-and-gap.md#capital-per-seller-s1); with an exact forecast a channel locks less). (4) An agent on Base only holds a `0x` key; NEAR is its netting layer. On `x207-v014.testnet` an EVM agent with a new key (not a public test key) joined with `join_evm` ([`E5dQ4Wn4TZyFUXheKvS1CS7whUaLHJ8sXp8hZ2zQJN3c`](https://testnet.nearblocks.io/txns/E5dQ4Wn4TZyFUXheKvS1CS7whUaLHJ8sXp8hZ2zQJN3c)), signed an EIP-712 voucher, was netted in epoch 2 and claimed to its own account with `claim_evm` ([`ERoUbiz3U2MgCkWR8YDuhzria7j8RvwYE8NCvvpziQMm`](https://testnet.nearblocks.io/txns/ERoUbiz3U2MgCkWR8YDuhzria7j8RvwYE8NCvvpziQMm)). The agent's `0x` key then spent its own payout through its NEAR eth-implicit account (NEP-518, `rlp_execute`: [`J59PWbv4MHUz2o7DPJcNk1fUZGrnZc8xy7N39VTXwx6m`](https://testnet.nearblocks.io/txns/J59PWbv4MHUz2o7DPJcNk1fUZGrnZc8xy7N39VTXwx6m)); any NEAR account can submit that transaction and pay the gas, only the `0x` key can authorize it. The limits: a relayer still paid the join deposit and the gas, funded the stake and registered the vouchers (the full circle flow through `rlp_execute` is not tested); the token is a mock USDT; settling from the stake ran once on testnet in contract 0.0.15: an EVM agent that never paid its residual had 20000 taken from its stake by `finalize_epoch` and stayed active (`FoH49TfgQuYR2iG5HjoUEjXercyDynh7pKANKAEzLVek`) (CT-108, [below](../README.md#settling-from-the-stake-opt-in)), and the funding route from other chains is mainnet and not tested. The relayer plays the role that the [x402 `exact` scheme on NEAR](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_near.md) gives to the facilitator (it sponsors the gas and the 1 yoctoNEAR deposit); a fee for it is live on `x207-v016.testnet` (contract 0.0.16, testnet only, one run) and does not exist in `x207-v014.testnet` or `x207-v015.testnet` ([who pays the relayer](evm-agents.md#who-pays-the-relayer-the-facilitator-role)). All hashes: [evm-agents.md](evm-agents.md).

## Status of every circle

Hackathon prototype for NEAR HACKATHON (1–14 Nov 2026). The contract (interface 0.0.13, release v0.0.13) runs as the circle `x207-v013.testnet` on NEAR testnet with a dashboard, a read API and an MCP server on top. Two newer circles run the later releases: `x207-v014.testnet` (v0.0.14, EVM members) and `x207-v015.testnet` (v0.0.15, settling from the stake); the dashboard picks the circle with `?circle=v013`, `?circle=v014` or `?circle=v015`, and each has its own read API. Two later releases run on testnet without a dashboard option yet: `x207-v016.testnet` (v0.0.16, a relayer fee on `claim_evm` and `withdraw_stake_evm`; no hosted read API) and `x207-v017.testnet` (v0.0.17, tag `v0.0.17`, wasm sha256 `cbb8a9108f975ba8fca86dc6f6d470e3e377b91309fce56b2ec18a77ff4a4b97`, the fee also on `request_exit_evm` and `set_auto_settle_evm`; its read API is [v017.x207.boxd.sh](https://v017.x207.boxd.sh/x207/circles/agents-main/epochs), BE-103). The integration tests run in a local `near-sandbox`, and the end-to-end sandbox workflow of this repository passed on GitHub on 2026-11-08 for the commit `5567e5b`, all five shards ([run 42467676597](https://github.com/x207-labs/x207/actions/runs/42467676597)). **No mainnet transaction has been sent.** **The team's keeper moves the epochs of `x207-v013.testnet` until 2026-11-18.** A worker run by the team (`scripts/keeper.mjs`, on a boxd machine) calls `close_epoch`, `commit_epoch` and `finalize_epoch` after each cutoff, so the dashboard can show an epoch that has just passed its cutoff or is waiting in a window. After 2026-11-18 the worker is stopped; the contract has no paid keeper, and anybody can move the epoch: see [how to move an epoch yourself](join-the-circle.md#move-the-epoch-yourself). The USDT on testnet is a **mock USDT** (testnet, `usdt.x207-deployer.testnet`): anybody can mint it, so no amount in this README is real money.

## Contract 0.0.18: sale of a NEAR account through a locker

Barter kinds #11 and #14, the fixes of the audit, `near-sdk` 5.30.1 (P1).

Built and tested on the branch `p1-0.0.18` of `contracts`: a locker contract that holds the sold account and releases a full-access key to the buyer only when the circle says so (`ed04e15`), an escrow of kind `account` in the circle (`6ad63e9`), and `near-sandbox` tests of a sale (#11) and of the sale of a member account that waits for the epochs to be final and rotates the voucher key (#14) (`b5e531e`). Fix of audit finding A-CT-01 (joins that never stake could hold all 64 slots): `remove_pending` and `make_room`, with a garbage-collection delay of 7 days that the owner can set between 1 hour and 30 days; a squatted slot still costs the 0.35 NEAR join deposit, so the attack is delayed, not made impossible. `near-sdk` 5.30.1 and `near-workspaces` 0.24.0 (CT-122). `wee_alloc` stays: it is the default allocator of `near-sdk`, there is no supported switch, and its advisory (RUSTSEC-2022-0054) is an "unmaintained" notice, not a vulnerability. A limit on the escrow (CT-129): it lasts at most `max_escrow_ttl` (default 72 hours, the owner can set 1 hour to 30 days; longer grants are refused with `ERR_ESCROW_TTL_TOO_LONG`), but the seller still cannot take the account back before the expiry. Contract tests as logged by the contracts session (not re-run for this README): the full suite 732 passed and 0 failed on contracts `1f30269`, among them 9 sandbox tests of the account escrow and 4 of `remove_pending` (one with 64 squatters).

**On testnet:** `x207-v018.testnet` (owner `x207-v18-own.testnet`, tag `v0.0.18`), circle wasm sha256 `4701ecce4168d18b0674b6b4af9f789219afc33be99d89c09f3a433c0bd0d198` built twice byte-identical from contracts `f551f51`, locker wasm sha256 `6d2ebdf437471a666bf9073637e012c04189cab08921e606ddbfec0bd9524e71`.
