# Security review, batch 4 (UM-063): claims of a delegate order and proofs of the grantee

Scope, read only: the backend half of the delegate order (BE-055 fix, `9017a33`, read again at `9a7f72d`): `backend/src/marketplace/order-claims.ts`, the claim and proof paths of `orders.ts` and `order-proofs.ts`, and the table `order_claims` in `migrations.ts`. And the proof of the `grantee_ref` of the access rent (BE-057 fix, `4030757`): `backend/broker/src/provider/` (`manager.ts`, `routes.ts`, `github.ts`, `ssh.ts`, `discord.ts`, `ssrf.ts`, `adapter.ts`) with `sdk/packages/core/src/grantee-proof.ts`, which the adapters call. The reviewer is the session that wrote the SDK half (Main B), not the author of the backend (Main C). Nothing in the backend or in the broker was changed. The facilitator of frozen accounts (SD-074) is not here: it is by the same session and it went to batch 5.

Levels as in batch 2: High = money or a proof can be forged by the other party with no cooperation; Medium = a documented guarantee does not hold under a plausible setup, or a party can gain with it; Low = hardening; Info = a limit to write down. Every finding below was reproduced with a throwaway test (run, then deleted: the test files were in `agents/test/`, using the real order book of the backend, and the real `GithubAdapter`, `SshAdapter` and `DiscordAdapter` with a mock `fetch`) **or** is marked "read from the code". Nothing was run against the real GitHub, Discord, or a NEAR node.

Checked and found sound: the challenge (16 random bytes, one per grant, 15 minutes, used up by the first proof that is checked, text bound to circle, grant, reference and nonce, so a proof of one grant is worth nothing for another); the third party cannot use it up (the `payer` of the voucher must be the grantee before `grantAccess` runs, `routes.ts:171`); the gist is read from `https://api.github.com/gists/<id>` only, the id comes from the proof by a regular expression and the host does not, through a guard that resolves the name, refuses one private answer among public ones, connects to the address it checked (the `lookup` hook checks again), refuses redirects, ports other than 443, credentials, and bodies above 256 KiB or 5 seconds; the owner of the gist is compared without case (GitHub logins are case-insensitive) and an anonymous gist is refused; the signature is checked against the registered voucher key of the grantee with the same NEP-413 scheme as the notices, and a file with a wrong or malformed signature is `bad_signature`, not a pass; the SSH key of the reference is parsed to its type and blob (the comment, options and newlines cannot ride in it; `parsePublicKey` rebuilds `type base64`), the forced command refuses quotes, backslashes and control characters, and the line carries `restrict` and `expiry-time` so the provider closes the access by itself; the lines are found by the suffix ` x207-grant-<id>`, with the leading space, so grant 1 does not match grant 11; the claim checks, in this order, that the transaction exists and every receipt succeeded, the signer, the receiver, one `FunctionCall` of the method of the order, `VoteApprove` or `VoteReject`, a non-negative integer id, the block time, and the proposal kind against the mandate, and the table has `PRIMARY KEY (circle_id, order_hash, proposal_id)` and `UNIQUE (circle_id, tx_hash)`, so a double claim never reaches the payment list; the RPC address of the claim comes from the configuration (`jsonRpcClaimRpc(primary)`) and never from a request; an NEP-366 delegate action, a batch of actions and a call to another method are `not_a_vote`.

## B4-F1 (Medium): a pending invitation is not cancelled after a restart
`GithubAdapter.grant` keeps `invitationId` in the map `#handles` (`github.ts:48,105`). The handle itself is `gh:owner/repo:login` and has no id. `#decode` (`github.ts:114-121`) rebuilds the target from the handle after a restart with `invitationId: null`, and `revoke` (`:130`) cancels an invitation only when it has the id. So after a restart `revoke` sends only `DELETE …/collaborators/{login}`. The comment on `#decode` says "the handle says what to remove, so a restart of the broker does not lose it"; the id is exactly what is lost. A collaborator invitation in GitHub stays valid for seven days until it is accepted, and `status()` (`:134-139`) answers `absent` for a user who has not accepted (`GET …/collaborators/{login}` is 404 before), so the sweep of the manager sees nothing left to remove.
Test (run): grant with a mock that answers `201 {id: 4242}`, then a second adapter (the restart) revokes the same handle. Calls of the first adapter: `PUT /repos/x207-labs/contracts/collaborators/alice-dev`. After the restart: only `DELETE /repos/x207-labs/contracts/collaborators/alice-dev`. In the same process the three calls are `PUT`, `DELETE …/invitations/4242`, `DELETE …/collaborators/alice-dev`.
Not run against GitHub: whether `DELETE …/collaborators/{login}` cancels a pending invitation is **not checked** here; the documentation of GitHub names the invitations endpoint for that. If it does cancel it, this finding is a Low.
Impact: the lessee waits for the end of the rent, accepts the invitation, and has the repository for free until the grantor notices. It needs a restart of the broker (or a crash) between the grant and the end of the rent.
Fix: put the id in the handle (`gh:owner/repo:login#4242`) or in the table `provider_access`, or, on `revoke` without an id, read `GET /repos/{owner}/{repo}/invitations` and cancel the one for the login. Owner: Main C.

## B4-F2 (Medium): shared handle, and the removal of what was there before
The handle is built from the target and the login only (`github.ts:99`). Two grants for the same login and the same repository give the same handle, so `revoke` of the first (its rent is over) removes the collaborator that the second one still pays for. And when the login is already a collaborator, GitHub answers `204` to `PUT …/collaborators/{login}`; the adapter notices (`delivery.invitation: "already_collaborator"`, `:106`) but `revoke` removes the collaborator anyway. For an organization seat (`:108-110,126-128`) `DELETE …/memberships/{login}` removes the member from the **whole organization**, not only from what the grant gave.
Test (run): two grants with ids 1 and 2 for `alice-dev` on `x207-labs/contracts` give the equal handle `gh:x207-labs/contracts:alice-dev`; a grant on a login that the mock calls an existing collaborator (`204`) answers `already_collaborator`, and its `revoke` sends `DELETE …/collaborators/bob-dev`.
Impact: the grantor can cut its own people (it names the `grantee_ref` of the grant, so this is its own mistake) and a second lessee can lose access because of the first. A lessee cannot choose someone else's login (it has to prove it owns it), so no stranger is hurt.
Fix: include the grant id in the handle and in the state; record `already_collaborator` and a seat that was there before, and do not remove those at the end of the rent (say it in the delivery); refuse a second active grant for the same `(provider, resource, grantee_ref)`. Owner: Main C.

## B4-F3 (Low): a `status` that is a string passes
`isFailure(tx.status)` is true only for an object with the key `Failure` (`order-claims.ts:58,120`); the only other condition is `tx.status === undefined`. The RPC `tx` has the final statuses `SuccessValue` and `SuccessReceiptId` (objects) and the non-final strings `NotStarted` and `Started` (and `Unknown`). The claim asks `wait_until: "FINAL"` (`:39`), which should not return a non-final transaction, but the check does not depend on that.
Test (run): the claim with a mock RPC that answers `status: "Started"`, `"NotStarted"` and `"Unknown"` is accepted (`201`) for a vote that is otherwise valid.
Impact: only if a node answers a non-final transaction as final. The vote could still fail later and the claim stays listed, which makes the buyer pay for a vote that did not happen.
Fix: accept only an object with `SuccessValue` or `SuccessReceiptId`; everything else is `tx_failed` (or `tx_not_found` for the non-final strings, so the delegate can try again). Owner: Main C.

## B4-F4 (Low): two claims at the same time end in a 500
The checks of `already_claimed` (`order-claims.ts:110,145`) and the insert (`:158-161`) are separated by awaits (`rpc.tx`, `blockTimestampNs`, and `chainView` for a proposal whose kind is not cached). Two requests for the same proposal with two transactions pass the check together and the second insert breaks the primary key.
Test (run): a mock `chainView` that waits 80 ms, two claims at once for proposal 7 with two different transactions: the answers are `201` and `500 internal_error: Kesalahan internal`.
Impact: no double payment, because the key stops it. The delegate sees an internal error instead of `already_claimed` and may retry for nothing; the log has a SQLite error with no context.
Fix: catch the constraint error of this insert and answer `400 claim_invalid` with `already_claimed` (or take the check and the insert in one `better-sqlite3` transaction after the awaits). Owner: Main C.

## B4-F5 (Low): an SSH key that can never be proven
`KEY_TYPES` (`ssh.ts:27-33`) lists `ssh-ed25519`, `ecdsa-sha2-nistp256`, `ecdsa-sha2-nistp384`, `sk-ssh-ed25519@openssh.com` and `ssh-rsa`, and `verifyGranteeRef` accepts all of them. `proveGranteeRef` calls `verifySshProof`, which calls `parseSshEd25519` and refuses every type but `ssh-ed25519` (`grantee-proof.ts:132-142`; the doc says so: "only ed25519 keys"). So a grant that names an RSA or ECDSA key is accepted on the chain and by the broker's first check, and then every `POST …/access` fails with `grantee_ref_unverified`: the lessee finds out when it tries to pay.
Test (run): `SshAdapter.verifyGranteeRef(<ssh-rsa line>)` is `{ok: true}`; `proveGranteeRef` for it throws `grantee_proof_bad_format: grantee_ref bukan kunci OpenSSH ssh-ed25519`.
Fix: `verifyGranteeRef` of the SSH adapter refuses what `proveGranteeRef` cannot prove, with a reason, so the grantor sees it before the offer is made (the frontend page of the grantor can show the same rule). Owner: Main C (adapter) and Main B (the page of the grantor).

## B4-F6 (Low): the challenge is burned by errors that are not the lessee's
`#takeChallenge` reads the row and deletes it (`manager.ts:232-238`) before `proveGranteeRef` runs (`:181`). A GitHub answer of 5xx or 403, a timeout, or a gist that is not public yet burns the challenge, and the lessee has to fetch a new one, make a new gist and sign again. The gist is read without a token (`guardedGet`, `github.ts:85`), and GitHub gives 60 requests an hour for an address that does not send one, shared by every grant that the broker serves. Read from the code; the rate limit was not met.
Fix: delete the row only when the proof was **checked** (passes, or fails for a reason that belongs to the proof: owner, challenge, signature), and keep it on `grantee_proof_unverifiable`; send the token of the grantor with the gist request (the token is for the API, not for the gist owner). Owner: Main C.

## B4-F7 (Low): "unproven" is a quiet path
`DiscordAdapter.proveGranteeRef` answers `{unproven}` when no OAuth verifier is installed (`discord.ts:64-66`), and the manager opens the access with `warnings: ["grantee_unproven"]` and `proof: "unproven: …"` (`manager.ts:186-189`). That is the documented behaviour (README of the broker). Two things follow: the warning is in the answer of the paid `POST` only, and the view keeps the text `proof`; and an adapter with no `proveGranteeRef` (S3 presigned, AWS STS) leaves `proof: null` with no warning at all (`manager.ts:176`), which the page of the renter shows as "no information", not as "not proven". The frontend (FE-029) shows `proof` and explains `grantee_unproven`; it does not tell `null` from an unproven reference.
Fix: give `proof` a value for the adapters that have no proof (`"none: …"`), and say in the README of the broker which providers can be proven at all. Owner: Main C (value) and Main B (page).

## B4-F8 (Info): the key of the proof is read from the read API
`voucherKeyOf` fetches `…/members/{account}` from the read API of the configuration (`broker.ts:77-80`) and the signature in the gist is checked against that key. The broker is run by the grantor, who also chooses the read API, so it trusts its own backend. The lesson of F1 of batch 3 is that a key shown by an API should be read from the contract when a signature depends on it. Here the read API and the broker have one operator, so the gain is small; write it in the README of the broker, or read the key with the `member` view of the contract (the broker already has `rpcUrl`).

## B4-F9 (Info): one vote pays one order
`UNIQUE (circle_id, tx_hash)` makes a transaction claimable once in the circle, and the vote of one account on one proposal cannot be repeated on the DAO. If the same delegate is hired by two buyers for the same DAO, each proposal pays only the order that claims it first; the other buyer gets nothing for that proposal. This is the safe side (no vote is sold twice), and the delegate picks who gets it. The status of the proposal (`InProgress`, `Rejected`, `Removed`) is not read: a vote is paid whatever happened to the proposal. Say both in `docs/order.md`.

## B4-F10 (Info): concurrent first requests
`grantAccess` reads `existing` (`manager.ts:172`) and saves at the end (`:211`) with awaits in between. For a provider that needs a challenge the second request fails at `#takeChallenge`. For the others (`mock`, `discord`, `s3-presigned`, `aws-sts`) two paid requests of the same lessee at the same time both call `adapter.grant`, and the second `#save` replaces the handle of the first: a session or a URL of the first call cannot be revoked by the handle (and these two cannot be taken back anyway). It costs the lessee two days for one. Read from the code, not run.
